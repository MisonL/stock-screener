# 系统架构

## 服务拓扑

五个容器，只有 `cloudflared` 对外：

```
                    Cloudflare
                        │
                  cloudflared
                   ┌────┴────┐
                   ▼         ▼
              stock.*      ntfy.*
                   │         │
                   ▼         ▼
              ┌────────┐  ┌──────┐
              │  api   │  │ ntfy │
              │ :5000  │  │:2586 │
              └───┬────┘  └──▲───┘
                  │          │
              ┌───┴────┐  ┌──┴─────┐
              │  jobs  │  │ agent  │
              └───┬────┘  └──┬─────┘
                  └────┬─────┘
                       ▼
                 market.db (SQLite)
```

| 服务 | 作用 | 是否碰上游 |
|---|---|---|
| `api` | 网页后端 + 健康检查 + watchdog | 否 |
| `jobs` | 调度器：盘中快照、盘后选池、清理、备份 | **是**（唯一的数据抓取方） |
| `agent` | LLM 盯盘：事件回合、聊天 | 是（经 jobs 的快照缓存） |
| `ntfy` | 推送服务端（自建，手机装 App 订阅） | 否 |
| `cloudflared` | 隧道，把内网服务映射到域名 | 否 |

**api 端口不发布到宿主机**——唯一入口是隧道。这样即使服务器在公网，也没有裸露端口。

## 数据流

```
上游（腾讯/新浪/westock）
        │
        ▼
   jobs 抓取 ──► snapshot_cache（快照，内存 + 表）
        │              │
        │              ├──► event_log（异动事件）
        │              │         │
        ▼              │         ▼
  daily_bars           │    signals（信号）
  corporate_actions    │         │
        │              │         ▼
        ▼              │   push_log（推送记录）
   盘后选池 ──► pool    │         │
        │              │         ▼
        └──────────────┴────► notify/（模板渲染）──► ntfy ──► 手机
                                          ▲
                                          │
                                     agent 回合
                                    （LLM 决策）
```

**单一抓取方**：所有上游请求都由 `jobs` 发出，`agent` 只读快照缓存。这样限速只有一处、上游调用可以被统一记账（`upstream_calls`），也避免两个进程同时打一个源。

## 代码结构

```
core/       基础设施：时钟与交易日历、DB 连接与迁移、配置、HTTP 限速、复权
  strategy/ 因子计算、打分、选池（纯函数为主，可单测）
  datasource/ 上游适配（腾讯、新浪、westock），统一 registry 与降级
jobs/       调度与批处理：盘中 tick、快照循环、盘后 EOD、清理、备份、归档
agent/      LLM 回合：注意力、工具调用、记忆、推送
llm/        模型客户端、预算、工具 schema 与注册表
notify/     推送：模板渲染、去重合并、ntfy 客户端
api/        网页后端：路由、鉴权、watchdog
web/        React 前端（Vite）
mcp/        westock MCP 封装（自选股等个人数据）
scripts/    运维脚本：发布、部署、验收
```

## 关键设计决策

### 秒级 tick 与写锁

`jobs` 有一个每秒跑的 tick，和 30 秒的心跳、盘后 EOD、清理任务**共用同一个 SQLite 连接**。SQLite 的事务是连接级的，两个线程在同一个连接上交替 `with conn:` 会让对方的中间状态被提前提交。

因此所有写库任务都必须持同一把写锁（`loops.lock`，也就是 `IntradayTick.lock`）。

**推论**：网络 I/O 绝不能放在锁内。抓几十个板块要好几分钟，占着写锁会把 tick 和心跳全堵死。正确做法是「先抓完、再加锁写」——`jobs/eod.py` 的 `fetch_sector_members` / `write_sector_members` 就是这么拆的。

这条有专门的 AST 守卫测试（`test_every_db_writing_job_holds_the_shared_write_lock`），按**调用点**判定，而不是「函数里出现过锁就放过」。

### 为什么用 SQLite 而不是 Postgres

单机、写入集中在盘后、读多写少、总量约千万行。SQLite 的 WAL 模式足够，且省掉一个常驻服务与它的运维成本。

代价是：不支持并发写、`WITHOUT ROWID` 表的索引选择很关键、需要显式维护统计信息。这些都写在 `core/db.py` 的注释里。

### 交易日历从数据来，不从配置来

`TradingCalendar` 的交易日列表来自 `daily_bars` 里 `sh000300` 的实际 bar。不维护一份手工日历，因为它总会过期。

**推论**：任何「判断今天是不是交易日、然后去写今天数据」的逻辑都会陷入鸡生蛋——今天的 bar 正是那个任务写的。所以这类判断必须走 `is_trading_day()`（对超出日历末日的日期按工作日 + 内置节假日兜底），而不是 `today in calendar`。

### 判活看文件修改时间，不看文件存在

`/tmp/jobs_healthy` 每 30 秒被 touch，Docker healthcheck 判「最近 2 分钟刷新过」。只判存在的话，主循环卡死时文件永远在、检查永远绿。

这个 touch 由**独立任务**执行，不碰数据库、不碰写锁——否则 EOD 持锁几分钟期间它会跟着停摆，容器被误判 unhealthy。

### 版本号必须有运行时出口

`core/version.py` 是版本号的唯一来源，`/healthz` 返回它。只在文件里写个数字、没有地方读，等于装饰。

## 时间与截止

| 时刻 | 任务 | 关键约束 |
|---|---|---|
| 08:40 / 08:46 | westock token 续期（失败重试） | 与交易日历无关（token 到期日可能是周末） |
| 08:50 | 刷行业成分股 | **先抓后写**，不把请求放锁内 |
| 08:55 | 自检（数据完整性、上游可达性） | |
| 09:00 | 导入手机自选股 | 只增不改 |
| 09:15–11:30 | 盘中快照 + 异动检测 | tick 每秒（interval 任务，非 cron），快照按 scope 分频 |
| 09:25:30 | 集合竞价采集 | 只此一次，窗口很窄 |
| 13:00–15:05 | 下午盘继续 | 同上；午休不跑，避免空转 |
| 15:05 | 盘后 EOD | 增量写 bar、算复权、选池；**持锁约数分钟** |
| 15:10 | 收盘小结推送 | |
| 15:30 | 归档 agent_turn | 三步操作必须原子（插归档→置空→删原表） |
| 16:00 | 清理 | 写多张表 + `PRAGMA optimize` |
| 23:30 | 备份 + 完整性校验 | 失败发 P0 |

「跑一次就失效」的任务（如启动补跑）必须回答：**进程在那个时刻不在会怎样？** 所以续期有 cron + 启动补跑两重保险，且启动补跑的时刻要在启动恢复**之后**重算——否则启动恢复耗时几十分钟后，那个时刻早就过期，任务会被调度器静默丢弃。
